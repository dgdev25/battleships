# Bugfix impact analysis — repeat-play sluggishness

## Target and dependency map

- `public/app.js` owns the page lifecycle: grid listeners are installed once at boot, `engage()` starts/restarts the one clock interval, `shoot()` sequences both impacts, and `renderGame()` updates all long-lived UI.
- `public/fx.js` is called only by `shoot()`. It owns short-lived impact nodes, geometry reads, animation timers, and the persistent one-per-board effect layers.
- `public/sfx.js` is called by boot visibility handling, the sound control, `engage()`, and `shoot()`. It owns one lazy `AudioContext`, one master/limiter graph, cached noise buffers, and short-lived sources.
- `public/scoreboard.js` is called by `renderScoreboard()` and the two hit paths. It owns the persistent segment DOM and its finite flash animation.
- `public/styles.css` drives the two visible looping ornaments, transient hit animations, and ship/wreck paint. Non-composited infinite animation here can consume CPU/GPU without growing the JS heap.
- `src/server.mjs` owns the in-memory `games` map and deletes completed games; abandoned games expire. It calls `Memory` and `Opponent` on every shot.
- `src/memory.mjs` owns the persistent ruvector indexes and append-only journals. Its size intentionally grows between completed games; resetting memory recreates both stores.
- Shared state/implicit contracts: one active client game, one active clock, one audio context per page, effects must self-remove, a shot remains locked until both impact sequences finish, hidden tabs must park audio/clock/animations, and server snapshots must not reveal enemy placement before game-over.

## Root-cause evidence and blast radius

The recent performance commit shows the strongest causes of the reported machine-wide sluggishness in the prior runtime: every sunk cell animated a non-composited `box-shadow` forever; the hidden radar arm kept rotating; deployment hover repainted all 100 cells; fleet/scope nodes were repeatedly rebuilt; noise buffers were synchronously regenerated per sound; and completed server sessions accumulated. Those paths are now bounded or cached. They explain high sustained render/audio-thread work after a game more convincingly than a growing JavaScript heap.

- High risk: firing timing and busy-state release; audio graph/source cleanup; hidden-tab lifecycle; game-over/new-game transition; enemy-information secrecy.
- Needs testing: visual-effect cleanup, ship overlays across resize/orientation, mute state, score updates, abandoned/finished server sessions, memory growth across games.
- Safe: pure battleship placement/fire rules and AI targeting semantics; this feature pass does not alter them.
- Unknown until browser measurement: GPU/render cost of gradients, shadows, and the permanent scope sweep; actual decoded sample memory after repeated shots.

## Safety constraints

- No more than one clock interval and one `AudioContext` may exist per page.
- Every transient effect node and every scheduled audio source must have a bounded lifetime.
- Hidden tabs must suspend audio and pause decorative animations.
- A player cannot fire twice while either missile/impact sequence is active.
- Hits, misses, sunk ships, score, seal verification, and game-over must remain identical to the server response.
- Enemy hull shapes may appear only when the server has revealed them at game-over.
- Existing user edits in `public/app.js`, `public/sfx.js`, `public/scoreboard.js`, and `public/styles.css` must be preserved.
- Must-pass checks: game-rule tests, API full-game flow, client regression tests, syntax checks, live browser console/network checks, repeated-shot DOM/heap sampling, and a performance trace.
- Rollback: the feature changes are isolated to client modules/styles plus a public-domain audio asset; revert those paths and remove the asset/attribution without touching game data or ruvector journals.
